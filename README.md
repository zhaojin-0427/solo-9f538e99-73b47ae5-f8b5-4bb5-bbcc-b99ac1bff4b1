# 药品稳定性试验 · 数据文件登记与追溯平台

药品稳定性试验的数据工程师发现一份**原始测量 CSV** 有误，需要阻止建模组继续使用
由它派生的**清洗表**和**批次汇总**。本平台用 Flask + SQLite 实现三类 CSV 文件的
登记、依赖追溯、撤销级联与下载资格控制。

## 1. 需求与实现对照

| 需求 | 实现方式 |
| --- | --- |
| 上传原始测量 / 清洗表 / 汇总 CSV | 首页表单选择类型上传，仅接受 `.csv`，服务端做 CSV 结构校验（编码、表头、列数、空行） |
| 后两类登记准确父文件 ID | 清洗表、批次汇总必须填父文件 ID（支持空格/逗号分隔、多个父项）；原始测量禁止填父项 |
| 父项提交时必须可用 | 父项存在、自身未撤销、且所有祖先未撤销；检查在 `BEGIN IMMEDIATE` 写锁内完成 |
| 文件与依赖一经登记不可改 | 仅提供上传/撤销/下载/查看路由，无编辑删除接口；对象存储文件以 ID 命名且从不覆写；依赖表有主键与外键约束 |
| 撤销后直接/间接依赖立即停止下载 | 下载时递归 CTE 实时计算祖先撤销状态，撤销只置标志位，派生文件立刻被阻断，无需批量改动 |
| 撤销与下载并发时不泄露完整文件 | 见下节「下载与撤销一致性」：进程内下载闸门（`app/downloads.py`）以租约串行化放行与撤销，流传输逐块复查租约，撤销提交后新下载一律不放行，已在传的下载被明确完成或安全终止 |
| 页面列出受影响链 | 文件详情页用递归 CTE 列出全部下游路径（`A -> B -> C`）与受影响文件数；首页列出阻断来源 |
| 修复件使用新 ID，旧派生件不恢复 | ID 按类型自增（`RAW-0001`/`CLN-0001`/`SUM-0001`），修复上传必为新 ID；资格由不可变登记数据 + 撤销标志实时推导，旧文件不会因新上传而恢复 |
| 上传与撤销交错，不能发布引用已撤销父项的文件 | 所有写事务用 `BEGIN IMMEDIATE` 串行化，父项检查与登记在同一事务同一锁内，并发下要么拒绝上传、要么登记后子文件立即不可下载 |
| 写盘或登记失败不暴露半成品 | 先写私有暂存目录，校验通过后 `rename` 进对象存储，再提交事务；任何异常回滚并清理暂存/孤立文件；启动时清扫残留 |
| 重启后下载资格一致 | 资格完全由 SQLite 持久数据推导，无内存状态；重启后结果不变；启动清扫不触碰已登记对象 |
| 可实际启动的 Docker Compose | `docker compose up --build` 一键启动，数据持久化在命名卷 `stability_data` |
| 浏览器操作入口 | 纯服务端渲染 HTML（无外部 CDN 依赖），访问 `http://localhost:8000/` |

## 1.1 下载与撤销一致性（本次修复重点）

**原问题**：下载视图先做一次资格检查，再把磁盘路径交给 `send_file`；而
`send_file` 在视图返回之后才惰性打开并逐块读取文件。质控员在「检查通过 →
字节开始/持续外发」之间提交撤销时，没有任何机制复查状态，于是撤销提交后该下载
仍可能把完整 CSV 发完，且与撤销并发到达的新下载也可能被放行。

**修复方案**（`app/downloads.py` 的进程内 `DownloadManager`，配合路由与
`revoke_file`）：

1. **放行与撤销互斥排序**：下载在管理器锁内领取租约（lease）；撤销在同一把锁内
   把被撤销文件及其全部传递后代标记为 blocked，并取消这些 id 的在途租约。撤销一旦
   提交并完成标记，之后的 `admit` 一律返回空，**撤销后不会有新下载被放行**。
2. **流传输逐块复查**：`RevocableFileResponse` 每读 256 KiB 就复查一次租约。
   - 撤销发生在响应生成**之前**：路由直接返回明确的 `409 Download Revoked`，
     一个字节都不承诺；
   - 撤销发生在**字节已开始外发之后**：生成器提前结束，附件传输被截断，客户端
     看到的是失败/不完整下载（HTTP 层常表现为 `IncompleteRead`/连接中断），
     **绝不会保存出一份完整文件**；
   - 任何路径（含客户端断连、I/O 错误）都会释放租约，撤销等待不会因僵死下载挂起。
3. **撤销等待在途下载收敛**：`revoke` 标记 blocked 后等待受影响租约排空
   （`DOWNLOAD_DRAIN_TIMEOUT`，默认 15s，小于 gunicorn worker 超时）。即使个别
   慢速客户端超过等待时间，blocked 集合也已生效，新请求依旧被拒，超时只记日志。
4. **状态来源仍是数据库**：内存 blocked 集合只是关闭竞态窗口的缓存，应用启动
   （含重启）时由 SQLite 中的撤销标志与血缘递归 CTE 重建；资格判断不依赖任何内存
   状态，重启后结论不变。上传登记、`BEGIN IMMEDIATE` 写锁、血缘阻断等既有逻辑
   均未改动。

> 该管理器为**单进程内**状态，与部署形态匹配：`docker-compose`/gunicorn 使用
> 1 个 worker × 多线程，线程共享同一管理器；SQLite 本身也是单写者模型。数据库
> 资格闸门始终生效，因此即便将来扩为多 worker，撤销提交后的新请求仍会被数据库
> 判定拒绝，只是「在途流的即时截断」仅在持有该连接的 worker 内最强保证。

## 3. 启动方式

### 3.1 Docker Compose（推荐）

```bash
docker compose up --build
# 浏览器打开 http://localhost:8000/
```

- 容器内 gunicorn：1 worker × 8 线程（SQLite 单写者模型下足够，且写事务已串行化）。
- SQLite 数据库、对象存储、暂存目录均在命名卷 `stability_data`（容器内 `/data`），
  容器重建后数据与下载资格保持不变。
- 生产环境请通过环境变量覆盖 `SECRET_KEY`。

### 3.2 本地直接运行

```bash
pip install -r requirements.txt
python -m flask --app wsgi:app run --host 0.0.0.0 --port 8000
# 或：gunicorn --bind 0.0.0.0:8000 wsgi:app
```

数据默认写入工作目录下的 `data/`，可用环境变量 `DATA_DIR` 覆盖。
另可用环境变量 `DOWNLOAD_DRAIN_TIMEOUT` 调整撤销等待在途下载排空的秒数
（默认 15，需小于 gunicorn 的 `--timeout`）。

## 4. 浏览器操作流程

1. 首页“登记上传 CSV 文件”卡片：
   - 类型选**原始测量**，父文件 ID 留空，选择 CSV → 校验并登记，得到 `RAW-0001`。
   - 类型选**清洗表**，父文件 ID 填 `RAW-0001`，上传后得到 `CLN-0001`。
   - 类型选**批次汇总**，父文件 ID 填 `CLN-0001`，上传后得到 `SUM-0001`。
2. 任一文件行点“详情”：查看元数据（大小、SHA-256、时间）、直接父/子文件、
   以及“撤销影响链”中列出的全部下游路径。
3. 质控员在详情页填写撤销原因并确认：
   - 被撤销文件与其全部直接/间接派生文件的“下载”立即变为停用；
   - 页面显示完整受影响链与阻断路径。
4. 修复时重新上传修正后的原始测量，系统分配**新 ID**（如 `RAW-0002`）；
   基于新 ID 登记的新清洗表可正常下载，旧 `CLN-0001`/`SUM-0001` 维持停用。
5. 任何对已撤销/被阻断父项的新登记都会被拒绝并在页面顶部提示原因。

## 5. HTTP 路由

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/` | 上传表单、文件清单（含状态徽章）、审计事件 |
| POST | `/upload` | 校验并登记 CSV（multipart：`kind`、`file`、`parent_ids`） |
| GET | `/files/<id>` | 文件详情、父子关系、撤销影响链、撤销表单 |
| POST | `/files/<id>/revoke` | 质控员撤销（必填 `reason`），幂等 |
| GET | `/files/<id>/download` | 资格通过才返回附件；撤销后新请求重定向回详情并提示，若租约在响应生成前被取消则返回 `409`，在途流被截断 |

## 6. 数据模型要点

- `files`：文件 ID、类型、原始文件名、SHA-256、大小、对象存储名、撤销标志/时间/原因。
- `dependencies`：`(child_id, parent_id)` 有主键、外键和 `child <> parent` 约束，
  边一旦插入不可修改。
- `id_seq`：按类型的自增序列，`UPSERT ... RETURNING` 在写事务内分配 ID，进程安全。
- `audit_events`：上传/撤销审计。
- 递归 CTE 分别实现祖先阻断查询（含路径）与下游影响链枚举。

```bash
python -m pytest tests/ -q
```

覆盖内容（共 40 个用例，全部通过）：

`tests/test_service.py`（27 个，原有能力保持不变）：

- 三类文件链式登记与 ID 规则；修复件新 ID、旧派生件不恢复；
- 父项缺失/已撤销/被祖先阻断/原始文件带父项等拒绝路径；
- 撤销级联后三者立即停下载、影响链与阻断路径展示、撤销需填原因、重复撤销幂等；
- 菱形依赖下任一祖先撤销即阻断；
- 坏 CSV（空文件、仅表头、列数不一致、空行）与非 `.csv` 拒绝，且失败后
  对象存储、暂存目录、数据库均无半成品；
- 不存在任何编辑/删除路由，依赖边重复插入被数据库拒绝；
- 多线程**上传与撤销交错**（屏障同步 + 15 轮重复）：不存在“引用已撤销父项且
  仍可下载”的文件；
- 模拟进程重启（同数据目录新建应用实例）：下载资格完全一致，暂存残留被清扫、
  已登记对象字节不变。

`tests/test_download_revoke.py`（13 个，本次新增的下载/撤销一致性）：

- 正常下载字节级完整、租约在用后释放；
- 撤销提交后路由层与管理器层都拒绝新放行（含全部传递后代）；
- 在 WSGI 层确定性控制流位置：已在传的下载在撤销后**逐块截断**，收到字节严格
  小于声明长度，绝不会发完整文件；撤销等待租约排空；首字节前取消则零字节；
- 租约放行后、响应生成前被取消时路由返回明确 `409`；
- 祖先撤销同时取消多个后代租约；重启后 blocked 集合由数据库重建；
- 排空超时也不会重新放行；多轮下载/撤销交错只可能出现「拒绝 / 截断」，
  撤销后无新放行。

此外在 gunicorn（1 worker/8 线程，与容器入口相同命令）上做过真实 HTTP
端到端验证：

- 上传链、正常下载字节一致、撤销级联、**重启后资格保持**、修复流程；
- 9.6 MB 文件慢速下载中并发撤销：传输在约 3.1 MB 处被截断，随后新下载全部 302；
- 6 轮 × 5 个并行慢速下载对同一撤销：30 个下载无一在撤销后发完整文件；
- 20 轮下载/撤销**同刻屏障竞速**：结果仅为截断或拒绝，赛后新请求全部 302；
- 12 轮 HTTP 上传/撤销并发交错 + 菱形血缘：无「引用已撤销父项且可下载」的文件，
  对已撤销父项的新登记一律拒绝。

## 8. 已知限制（如实说明）

- 当前沙箱环境没有 Docker daemon，Dockerfile/compose 已做静态与等效流程验证
  （本地以 gunicorn + 相同入口命令跑通），但未在本环境实际执行 `docker build`。
- 平台未做用户登录与角色鉴权，“质控员撤销”是页面操作语义而非权限系统；
  如需多用户，应在反向代理或应用层补充认证。
- gunicorn 配置为单 worker 以契合 SQLite 单写者模型；读请求可通过多线程扩展，
  超高写入场景建议更换为 C/S 数据库。下载闸门的在途截断依赖单进程内共享状态，
  多 worker 部署时数据库闸门仍保证撤销后不放行新下载，但在途流的即时终止只在
  持有该连接的 worker 内最强保证（当前 Compose 为单 worker，无此问题）。
- 在途下载若在撤销后仍被逐块截断，已收到的前缀字节无法从客户端收回；平台保证的
  是「不产出完整文件、不放行新下载」，而非撤回已离进程的少量数据块（每块
  256 KiB）。对零泄露要求更高的场景应在下载前增加人工确认或令牌式授权。
